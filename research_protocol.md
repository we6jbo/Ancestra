# Ancestra — recurring Vibe research and DOCX update protocol (v0.7)

This file is managed by Ancestra and may be refreshed by newer versions. User-authored `plan.md`, `moltbook.md`, and `tree.md` must **never** be overwritten automatically.

## Mandatory order on every Vibe research session
1. Read `init.md` **and this file**, then `unconfirmed.md` and `confirmed.md` first. Read `plan.md`; if missing, interactively create it with Jeremiah. Confirm allowed research sites, search strategies, identities, records, dates and locations, privacy boundaries, and how to distinguish primary records from user posts or AI suggestions. Do not imply research has happened if browsing is unavailable.
2. Read `moltbook.md`; if missing, interactively create it. Before posting to Moltbook, propose a privacy-reviewed draft and obtain explicit approval for the exact content and scope; treat AI responses as research leads, not proof. Never publish private data or protected birth years **1981, 1960, 1926, 1928**. Do not disclose family information without approval.
3. Read `tree.md`; if missing, interactively create it. This is the research work queue: rank people with absent stories or missing parent/child links, record hypotheses, evidence, contradictions, next searches, and whether a lead should be accepted, rejected or held. Mark which person has been searched and what remains. Revisit it every session.
4. **EXTERNAL**: open `external/manifest.json` and read each listed `source` file. Match source claims to TG/AKA, document what was understood, cross-check claims against independent primary records, and use the findings to inform `tree.md`, approved Moltbook questions, and the DOCX. Only set `read_confirmed: true` after successful extraction and explanation, and only set `retained_confirmed: true` after that source has been integrated into durable research records with citations. Leave red when unverified. Preserve statuses and entries, never claim ChatGPT uploads automatically sync to this computer. The user must import new files with Ancestra or the installer. Record Moltbook `posted` evidence (URL/time) separately; `retained_confirmed` does not imply posting. Prior to ANY Moltbook posting, obtain explicit approval, and redact exact protected birth years 1981, 1960, 1926, 1928 and private living-person details.
5. **After the research steps, update `Ancestra_Manual_Updates.docx` EVERY session**, even when no new facts are verified. Preserve unresolved tasks from prior reports, add new findings and new people, and update existing sections rather than dropping old entries. Report the session date/time, sources checked, outcomes (including no-results), and the next manual actions for all people still needing them.

## What the DOCX must contain
- Executive tally: each person's name and TG/AKA, story status, parent/child gaps, and priority. Include existing and newly discovered people.
- For each actionable person: current source value; proposed field-level changes; **exact target** (`/tmp/kinmap_family_tree_26-27.json` and/or `/var/lib/kinmap/kinmap_state.json` or `/home/we6jbo/.family_story/real stories.db`), table/JSON path, TG/AKA code, evidence URL or citation, confidence (verified, plausible, disputed, unknown), and what Jeremiah must do using his existing editors. Prefer the persistent source of truth over an ephemeral `/tmp` file, once identified with Jeremiah.
- A draft story paragraph when evidence supports one, clearly labeled *proposed, not entered*. Preserve citations, spelling variants, historic places, and uncertainties. No biography based solely on a search hit, Reddit post, AI reply, or name match.
- Separate sections for **Ready for manual update**, **Needs verification**, **Unresolved**, and **Previously completed**. Carry forward tasks with their statuses; do not invent completed work. Record a dated changelog and the specific changes from the prior DOCX.
- Check the live data anew each session and use read-only access. Never directly write to KinMap state, tree JSON, or story database. Do not make claims based solely on stale cached copies without marking them cached. If DOCX generation tools are missing, give setup instructions and retain findings in a markdown draft; do not claim DOCX was updated.
- Treat *all* four birth years `1981`, `1960`, `1926`, `1928` as protected for public sharing. Keep local reports private; verify living-person privacy before public outreach.

## Repeatability and crash recovery
Keep timestamped, append-only research checkpoints in this directory for searches completed, sources used, prior status, and next step. On restart, read the checkpoint log and avoid repeating dangerous or irreversible steps. Maintain stable code identity by TG/AKA and do not conflate matching display names. Back up the existing DOCX before rebuilding it. The DOCX is a continuously maintained research checklist, not a one-time export.


## Researched tab state — `researched_status.json`
- Ancestra stores per-person `exhausted` and `interactive_requested` booleans keyed by TG/AKA when possible. `exhausted` means no further *currently available* credible leads, not proof of complete knowledge. A user can uncheck this anytime; Vibe should honor that as re-research priority.
- When `interactive_requested` is true, Vibe must have an interactive conversation with Jeremiah for that person and must not silently skip or auto-complete it. Only clear the request after Jeremiah explicitly confirms there is nothing more to add. Save new leads and revisit evidence.
- After re-research, Vibe may set `exhausted` true only if it actually repeated a good-faith search and found no new credible leads, recording its source coverage in tree.md; it must not change `interactive_requested` except on user confirmation.
- Do not overwrite existing research-status entries wholesale; merge changes. Ancestra may be open; avoid simultaneous writes, and refresh the tab when edits occur.

## External intake and provenance
- The bundled McCabe/Shapley/Schlorf note is USER-AUTHORED and not independent proof. Birthdates and links are investigative leads. Avoid public disclosure without privacy approval.
